# GenieLaw — Full Project Audit
**Date:** 2026-07-27 · **Branch:** `main` · **Scope:** Flutter app (`lib/`, ~200 files, 33k LOC in `features/`) + Node/Express backend (`backend/src/`)

---

## 0. Executive Summary

The app is feature-broad and visually ambitious — three role surfaces (client / lawyer / admin), ~70 screens, AI intake, chat, scheduling, documents. The **shell is far ahead of the plumbing**: navigation, state and UI are largely built out, but the security layer, the design system, and the dead-code situation all need real work before this touches production client data.

**Headline numbers:**

| Metric | Value |
| :--- | :--- |
| Dart files unreferenced (dead) | **65 of ~200 (~33%)** |
| `flutter analyze` issues | **313** (45 are hard compile errors) |
| Integration test suite | **Does not compile** |
| Hardcoded `Color(0x…)` literals | **578** |
| `Semantics` / `semanticLabel` usages | **0** |
| Files with responsive breakpoints | **5** |
| Critical security findings | **6** |

**The six things that must be fixed before any real client uses this:**
1. Password-reset OTP returned in the HTTP response → trivial account takeover of *any* account, including admin.
2. Socket.IO namespaces have zero authentication → any anonymous client can join any attorney–client chat room.
3. `GET /api/documents` returns **every document in the system** to any logged-in lawyer.
4. `/uploads` is served as unauthenticated static files → all legal documents publicly readable by URL.
5. Mass assignment on signup → self-register as a *verified* lawyer.
6. No rate limiting anywhere (the dependency is installed but never wired).

### 1.3 Structural inconsistency

| Severity | **Medium** |
| :--- | :--- |
| **Effort** | Needs rework (1–2 days) |

Three competing organisational conventions coexist:

1. **Clean-architecture** (`data/` → `domain/` → `presentation/`) — used *only* by `features/authentication/`
2. **Feature-flat** (`screens/`, `widgets/`, `providers/`, `models/`) — used by `features/client/*`
3. **Global buckets** — `lib/models/` (26 files), `lib/providers/` (23 files), `lib/repositories/` (10 files) sit outside the feature tree entirely

The result is that `authentication` has **two** auth providers:
- `lib/providers/auth_provider.dart` (global session state — the real one)
- `lib/features/authentication/presentation/providers/auth_provider.dart` (use-case wrappers)

`login_screen.dart:8` has to import both, aliasing one as `global_auth`. That is a smell you will keep paying for.

**Fix:** pick convention #2 (feature-flat) — it's what most of the codebase already uses — and migrate `lib/models`, `lib/providers`, `lib/repositories` into their owning features. Keep only genuinely cross-cutting items in `lib/core/`. Do this incrementally, one feature per PR.

### 2.2 Password reset is a dead end — the flow is fake

| File | `lib/features/authentication/presentation/forgot_password/forgot_password_screen.dart` |
| :--- | :--- |
| **Severity** | **Critical** (functionality) |
| **Effort** | Needs rework (1–2 days incl. email delivery) |

The screen is 196 lines of UI with **no network call at all**. The only `await` in the file is:

```dart
await Future.delayed(...)   // line 52
```

It fakes a delay and shows success. A user who forgets their password has **no recovery path whatsoever** — and is told it worked. Backend endpoints `/auth/forgot-password` and `/auth/reset-password` exist but are never called (and are themselves critically broken — see §6.1).

**Fix:** wire the screen to a real two-step flow (request OTP → verify OTP + set new password), and fix the backend to email the OTP rather than return it. This is a guaranteed support-ticket generator and a guaranteed drop-off point.

### 2.3 Messages is unreachable from the bottom nav

| File | `lib/core/widgets/app_shell.dart` |
| :--- | :--- |
| **Severity** | **High** (UX) |
| **Effort** | Quick fix (2–3 hrs) |

The bottom bar has four tabs — Home, My Cases, Advocates, Profile — plus a centre FAB for Post Case. `/messages` is registered as a **pushed** route only. For a consultation app, attorney–client messaging is a primary surface buried behind navigation.

Compounding it: because `/messages` is pushed with `parentNavigatorKey: _rootNavigatorKey`, it covers the bottom bar entirely. A user in Messages has only the system back gesture to return — and no unread badge anywhere to draw them in.

**Fix:** promote Messages to a 5th tab (or replace Advocates, which duplicates the Home category browse). Add an unread-count badge driven by `chat_provider`.

### 2.4 Splash uses a fixed 3-second delay racing an async auth read

| File | `lib/features/splash/presentation/screens/splash_screen.dart:33-36` |
| :--- | :--- |
| **Severity** | **Medium** |
| **Effort** | Quick fix (1 hr) |

```dart
Future.delayed(const Duration(seconds: 3), _handleNavigation);
```

`AuthNotifier.initialize()` is fired from the constructor and is `async` — nothing guarantees it has finished when `_handleNavigation` reads `authProvider` at t=3s. On a cold start with slow secure-storage (older Android, encrypted shared prefs), a logged-in user gets bounced to `/login`. And every user pays a flat 3s on every launch regardless.

**Fix:** expose an `isInitialized` flag on `AuthState`, and have splash `await` it (with a *minimum* display time of ~800ms for brand polish, not a fixed 3s).

### 2.5 Frontend admin routes have no role guard

| File | `lib/routes/app_router.dart:88-152` (`redirect`) |
| :--- | :--- |
| **Severity** | **High** |
| **Effort** | Quick fix (30 min) |

The redirect guards two cases:
- lawyer trying to reach a client route → `/client-dashboard`
- non-lawyer trying to reach `/lawyer-dashboard` → `/client-dashboard`

There is **no check on any of the 14 admin routes**. A logged-in client navigating to `/admin-dashboard` (deep link, or a stale link) passes every condition and renders the full `AdminShell`.

The backend *is* correctly protected (`admin.routes.js` applies `authMiddleware` + `roleMiddleware("admin")`), so no data leaks — the panels render empty or error. But it's a broken, confusing state that exposes your admin IA to end users.

**Fix:** add to the redirect, mirroring the existing lawyer guard:

```dart
const adminPrefixes = ['/admin-'];
if (adminPrefixes.any(path.startsWith) && role != UserRole.admin) {
  return isLoggedIn ? RouteNames.clientDashboard : RouteNames.login;
}
```

Note `lib/routes/route_guard.dart` is an **empty file** — this is clearly where it was meant to live.

### 2.6 Two navigation systems in one app

| Severity | **Medium** |
| :--- | :--- |
| **Effort** | Needs rework (1 day) |

27 `Navigator.push`/`MaterialPageRoute` calls coexist with 89 go_router calls (`context.go` ×21, `context.push` ×49, `context.pop` ×19), across 7 files:

- `ai_smart_case_intake_screen.dart`, `ai_smart_case_processing_screen.dart`, `ai_smart_questions_screen.dart`
- `profile_screen.dart`, `help_center_screen.dart`, `support_help_screen.dart`
- `lawyer/profile/lawyer_profile_screen.dart`

Consequences: those screens are **not deep-linkable**, are **not covered by the router's auth redirect**, and their back-stack behaviour diverges from the rest of the app.

This is why 17 screens exist that the router never registers — including the entire lawyer profile sub-tree (`LawyerReviewsScreen`, `LawyerDocumentsScreen`, `LawyerSettingsScreen`, `LawyerProfessionalDetailsScreen`, `LawyerConsultationSettingsScreen`, `LawyerMyProfileScreen`, `LawyerLeadsScreen`, `LawyerNotificationsScreen`) and the AI Smart Case funnel (`AISmartQuestionsScreen`, `AISmartCaseProcessingScreen`, `AICaseReviewScreen`).

**Fix:** register all 17 in `app_router.dart` and convert the 27 `Navigator.push` calls to `context.push`. The lawyer sub-tree especially — right now a lawyer's entire settings area sits outside your auth guard.

### 3.4 Responsiveness — effectively mobile-portrait only

| Severity | **High** (if tablet/web is in scope) · **Low** (if phone-only) |
| :--- | :--- |
| **Effort** | Needs rework (1–2 weeks for full tablet support) |

Only **5 of ~70 screens** use `LayoutBuilder` or any width breakpoint:
`advocates_screen`, `schedule_consultation_screen`, `ai_legal_assistant_card`, `premium_audio_player`, `contact_support_screen`.

Everything else is fixed-width `Column`/`Padding` tuned for a ~390pt phone. On a tablet the content stretches edge-to-edge with enormous line lengths; the admin panel in particular (5-tab bottom nav, data tables) is unusable at tablet width and is exactly the surface an admin would want on a larger screen.

That alone buys most of the benefit for modest effort.

### 3.6 Accessibility — essentially absent

| Severity | **High** |
| :--- | :--- |
| **Effort** | Needs rework (1 week) |

| Check | Result |
| :--- | :--- |
| `Semantics(` widgets | **0** |
| `semanticLabel:` properties | **0** |
| `tooltip:` properties | 5 |

**Concrete problems:**

1. **Screen readers get nothing.** Every icon-only control — the bottom-nav items, the FAB, appbar actions, the audio recorder in `post_case_screen` — is unlabelled. TalkBack/VoiceOver announces "button" with no context. For a legal-services app this is likely an accessibility-compliance exposure, not just a nicety.

2. **Tap targets below minimum.** `app_shell.dart:_NavItem` — a 24px icon + 3px gap + 11px text inside `EdgeInsets.symmetric(horizontal: 12, vertical: 8)` gives roughly **40px** of height. Material and iOS both require **48dp / 44pt**. Every bottom-nav tap is harder than it should be.

3. **11px nav labels** (`app_shell.dart`) are below the 12sp practical floor and don't scale — no `textScaler` handling anywhere in the app means users with large system font settings will get overflow, not reflow.

4. **Contrast needs verification.** The palette pairs gold `#DAA02F` on near-black `#0A0A0A` — that passes comfortably (~9:1). But `inactiveColor: Colors.grey` (`#9E9E9E`) on `Colors.black` in the nav bar is ~7:1 and fine, while grey-on-`cardBackground #171717` in various cards will be tighter. Audit the mid-greys specifically.

**Fix:** wrap icon-only controls in `Semantics(label: …, button: true)`, raise `_NavItem` padding to hit 48dp, bump nav label to 12sp, and run Flutter's Accessibility Guideline tests (`meetsGuideline(textContrastGuideline)`, `androidTapTargetGuideline`) in widget tests.

### 4.2 `TestApi.test()` fires on every widget rebuild

| File | `lib/app.dart:21` |
| :--- | :--- |
| **Severity** | **High** |
| **Effort** | Quick fix (5 min) |

```dart
Widget build(BuildContext context, WidgetRef ref) {
  final router = ref.watch(routerProvider);
  final languageState = ref.watch(languageProvider);
  TestApi.test();          // ← unguarded network call inside build()
  return MaterialApp.router(…);

```

`MyApp` is a `ConsumerWidget` watching two providers. Every language change, every router notification, every rebuild fires an un-awaited `GET /` and dumps status + body to `debugPrint`. It's debug scaffolding (`lib/core/network/test_api.dart`) that shipped into the app root.

**Fix:** delete the call and delete `test_api.dart`.

### 4.3 Silent exception swallowing

| Severity | **High** |
| :--- | :--- |
| **Effort** | Quick fix (2–3 hrs) |

`lib/core/storage/token_storage.dart` — **every one of its 13 methods** wraps its body in `try { … } catch (_) {}`:

```dart
Future<void> saveToken(String token) async {
  try {
    await _secureStorage.write(key: _tokenKey, value: token);
  } catch (_) {}          // ← failure is invisible
}
```

If secure storage fails (Android keystore issues after an OS upgrade are a known class of failure), `saveToken` silently no-ops. The user sees a successful login, `AuthState.isLoggedIn` is `true`, and then **every API call 401s** with no explanation and no way to recover except reinstalling.

Same pattern in `lib/providers/auth_provider.dart`:

```dart
} catch (e) {
  // Handle error        ← in updateUserProfile (line ~200)
}
return false;
```
and again in `updateProfileImage`. The user taps Save, nothing happens, no message.

**Fix:** let storage exceptions propagate (or at minimum log via the existing `core/utils/logger.dart` and surface a failure state). For the profile methods, return a typed result and show a `SnackBar` on failure.

### 4.4 No 401 handling — sessions die silently

| File | `lib/core/network/api_interceptor.dart` |
| :--- | :--- |
| **Severity** | **High** |
| **Effort** | Quick fix (2–4 hrs) |

`ApiInterceptor` only attaches the bearer token. There is **no `onError` handling for 401**. JWTs expire in 7 days (`JWT_EXPIRES_IN=7d`); on day 8 the user opens the app, `AuthState.isLoggedIn` is still `true` (the token string is still in storage), and every screen shows an error with no prompt to re-authenticate.

The backend's `POST /auth/refresh-token` is a **stub** that returns `{success: true, message: "Token refreshed."}` and issues no token (`authRoutes.js:60-63`, commented "Mock endpoint").

**Fix:** add a 401 branch to the interceptor that calls `authProvider.logout()` and redirects to `/login` with a "Session expired" message. Implement real refresh tokens when you can — but the logout path is the urgent part.

### 4.5 Validation gaps

| Severity | **Medium** |
| :--- | :--- |
| **Effort** | Quick fix (3–4 hrs) |

**Login validates password length** (`login_screen.dart:60-67`):
```dart
if (value.length < 6) return "Password too short";
```
Login should only check non-empty. This blocks any legacy user whose password predates the policy, and it advertises your policy to attackers.

**Email regex is wrong** (identical copy in both `login_screen.dart:44-46` and `signup_screen.dart:102-104`):
```dart
r'^[\w-\.]+@([\w-]+\.)+[\w]{2,4}$'
```
The `{2,4}` TLD bound rejects valid addresses: `.legal`, `.lawyer`, `.attorney`, `.agency`, `.consulting` — TLDs your actual user base plausibly uses. Also rejects `+` tagging (`user+case@gmail.com`).

**Password policy is 6 characters, no complexity** — frontend (`signup_screen.dart:~135`) and backend (`authValidation.js`) agree on `min: 6`. For an application holding privileged legal communications this is too weak. Recommend 10+ with a breach-list check.

**No lawyer credential collection at signup.** `signup_screen.dart` offers a `_selectedRole` toggle of `client`/`lawyer` and collects only name, email, mobile, password. **Zero** bar council number, enrolment number, jurisdiction, or practice certificate. A `POST /auth/signup` with `role: "lawyer"` creates a practising-advocate account instantly. There's an admin verification flow (`admin_lawyer_verification_screen`) but nothing forces a lawyer through it before they appear to clients.

**Document upload validation** (`post_case_screen.dart:1833-1836`) is the one bright spot — `FilePicker` restricted to `allowedExtensions: ['pdf']` with a 10 MB check at line 1733 matching the backend's multer limit. Good. But it's the only upload path that's this careful; `lawyer_documents_screen.dart` and the profile-image path are looser.

**No date validation anywhere.** `schedule_consultation_screen.dart` has no guard against booking in the past, and no timezone handling — a client and lawyer in different zones will see different times for the same appointment.

**Fix:** move all validation into the (currently dead) `core/utils/validators.dart`, fix the regex to a permissive RFC-ish pattern, drop the length check on login, raise the signup minimum, add conditional bar-council fields when `role == lawyer`, and add `firstDate: DateTime.now()` plus UTC storage on all scheduling.

## 6. Security & Compliance

This is a legal-services application holding privileged attorney–client material. The findings below are ordered by severity and all are exploitable as written.

### 6.1 🔴 CRITICAL — Password reset returns the OTP in the API response

| File | `backend/src/services/auth/authService.js` (`forgotPassword`) |
| :--- | :--- |
| **Severity** | **Critical** |
| **Effort** | Quick fix (2 hrs) + email delivery (1 day) |

```js
const resetToken = Math.floor(100000 + Math.random() * 900000).toString();
user.resetPasswordToken = resetToken;
user.resetPasswordExpire = Date.now() + 3600000;
await user.save();

return { resetToken };          // ← returned to the caller
```

The controller passes this straight into the HTTP response:
```js
return ApiResponse.success(res, "Password reset code generated.", result);
```

**`POST /api/auth/forgot-password` is unauthenticated.** Anyone who knows a target's email address receives that account's reset OTP directly in the response body, then calls `POST /api/auth/reset-password` with it. **Full account takeover of any user — including any admin — in two unauthenticated HTTP requests.**

Three aggravating factors:
- `Math.random()` is not cryptographically secure — even without the response leak, the OTP would be predictable.
- The 404 `"User with this email does not exist."` is a **user-enumeration oracle**.
- **No rate limiting** (§6.6), so brute-forcing a 6-digit OTP is trivially feasible anyway.

**Fix:**
1. Remove `resetToken` from the return value immediately — this one line is the whole exploit.
2. Generate with `crypto.randomInt(100000, 1000000)`, and store a **hash** of the token, not the token.
3. Email the OTP out-of-band.
4. Return an identical `200 "If that email exists, a reset code has been sent."` whether or not the user exists.
5. Rate limit to ~3 requests / 15 min / IP+email, and cap verification attempts at 5.

### 6.2 🔴 CRITICAL — Socket.IO has no authentication

| File | `backend/src/sockets/chat.socket.js`, `backend/src/server.js:16-21` |
| :--- | :--- |
| **Severity** | **Critical** |
| **Effort** | Quick fix (3–4 hrs) |

```js
chatNamespace.on("connection", (socket) => {
  socket.on("join", ({ chatId }) => {
    if (chatId) socket.join(chatId.toString());   // no auth, no membership check
  });

  socket.on("register", ({ userId }) => {
    if (userId) { socket.join(userId.toString()); … }   // join anyone's room
  });
```

There is **no handshake authentication** on the Socket.IO server, on any of the three namespaces (`chat`, `notification`, `case`), and **no membership verification** on join. CORS is `origin: "*"`.

An anonymous attacker can:
- Connect with no credentials
- `emit("join", { chatId })` for any conversation ID and **receive every live message in that attorney–client conversation**
- `emit("register", { userId })` as any user and receive their private notification stream
- Forge presence and typing indicators for any user

Chat IDs are Mongo ObjectIds — not secret, and exposed in client URLs (`/chat/:chatId/:lawyerName`). Any leaked or logged URL becomes a permanent live wiretap on a privileged conversation.

For a legal application this is a direct breach of attorney–client confidentiality.

**Fix:**
```js
io.of("/chat").use(async (socket, next) => {
  try {
    const token = socket.handshake.auth?.token;
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    socket.userId = decoded.id;
    next();
  } catch { next(new Error("Unauthorized")); }
});
```
Then in `join`, verify `socket.userId` is a participant of `chatId` before `socket.join()`. In `register`, ignore the client-supplied `userId` entirely and use `socket.userId`. Lock CORS to your known origins.

### 6.3 🔴 CRITICAL — Every lawyer can read every client's documents

| File | `backend/src/controllers/document/documentController.js` (`getDocuments`, `getDocumentById`) |
| :--- | :--- |
| **Severity** | **Critical** |
| **Effort** | Quick fix (1 hr) |

```js
async getDocuments(req, res, next) {

  if (req.user.role === "client") {
    query.clientId = req.user._id;
  }
  // ← lawyer / admin fall through with query = {}
  const documents = await Document.find(query).sort({ uploadedAt: -1 });
```

`GET /api/documents` with **any lawyer account** returns **every document uploaded by every client in the system**. A lawyer signs up (§6.4 — with no verification required) and immediately enumerates the entire document corpus.

`getDocumentById` and `deleteDocument` have the same shape:
```js
if (req.user.role === "client" && document.clientId.toString() !== req.user._id.toString()) {
  return ApiResponse.error(res, "Unauthorized.", 403);
}
```
The role check short-circuits for lawyers — so a lawyer can fetch **and delete** any document by ID.

Note `caseController.js` gets this right (scoping by `assignedLawyer`/`selectedLawyer` at lines 97-108, 627-632, 664-669). The document controller simply wasn't given the same treatment.

**Fix:** scope lawyers to documents attached to cases they're assigned to:
```js
if (req.user.role === "lawyer") {
  const caseIds = await Case.find({
    $or: [{ assignedLawyer: req.user._id }, { selectedLawyer: req.user._id }]
  }).distinct("_id");

} else if (req.user.role !== "admin") {

}
```
Apply the same to `getDocumentById` and `deleteDocument`.

### 6.4 🔴 CRITICAL — `/uploads` is unauthenticated static file serving

| File | `backend/src/app.js:78-80` |
| :--- | :--- |
| **Severity** | **Critical** |
| **Effort** | Needs rework (1–2 days) |

```js
app.use("/uploads", express.static(path.join(__dirname, "../uploads")));
```

Every uploaded artefact — client legal documents, case evidence, bar-council certificates, profile photos, voice recordings of case descriptions — is served **with no authentication at all**. Anyone with the URL downloads the file.

Filenames are `Date.now() + "-" + Math.round(Math.random() * 1e9) + ext` (`upload.middleware.js:29-31`), which is not secret, and the paths are stored in the database and returned in API responses that any authenticated user can trigger.

**Secondary issue — stored XSS.** The MIME allowlist in `upload.middleware.js` includes `"application/octet-stream"`, which any client can set on any file. Combined with `path.extname(file.originalname)` preserving the *original* extension, an attacker uploads `payload.html` as `application/octet-stream` and `express.static` serves it back as `text/html` on your origin.

**Fix:**
1. Remove the `express.static` mount.
2. Serve files through an authenticated controller that checks ownership before streaming (`res.sendFile` after the same authorisation as §6.3).
3. Better: move to signed, short-TTL URLs — Cloudinary is already a dependency and `cloudinary_service.dart` / `config/cloudinary.js` already exist (currently unused, credentials commented out in `.env`).
4. Drop `application/octet-stream` from the allowlist and normalise the stored extension from the *validated MIME type*, not from `originalname`.
5. Add `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`.

### 6.5 🔴 CRITICAL — Mass assignment on signup

| File | `backend/src/services/auth/authService.js` (`register`) → `userRepository.create(userData)` |
| :--- | :--- |
| **Severity** | **Critical** |
| **Effort** | Quick fix (30 min) |

```js
async register(userData) {          // userData === req.body, unfiltered
  …
  const user = await userRepository.create(userData);   // User.create(req.body)
}
```

`signupValidation` constrains `role` to `["client", "lawyer"]` — so admin escalation is blocked. But it does **not strip other fields**, and Mongoose accepts any key present in the schema. `User.js` includes:

```js
isVerified: { type: Boolean, default: false },
isActive:   { type: Boolean, default: true },
```

So `POST /api/auth/signup` with `{ …, "role": "lawyer", "isVerified": true }` creates a **verified lawyer account** in one unauthenticated request. `isVerified` is precisely the flag the admin verification flow sets (`adminController.verifyLawyer` → `User.findByIdAndUpdate(…, { isVerified: true })`).

The separate `Lawyer.verificationStatus` field would remain `"pending"`, so the blast radius depends on which flag your client-facing "verified advocate" badge reads — but the two are meant to move together and now don't. Either way an attacker controls a field the security model assumes only admins can set.

Combined with §4.5 (no credential collection at signup), the path from "stranger" to "verified advocate visible to clients seeking legal help" is a single HTTP request.

**Fix:** allowlist explicitly — never pass `req.body` to a create:
```js
const { fullName, email, mobile, password, role } = req.body;
const user = await userRepository.create({
  fullName, email, mobile, password,
  role: role === "lawyer" ? "lawyer" : "client",
});
```
Then require bar-council details for lawyer signups and gate visibility on admin verification.

## 8b. AI Smart Case Assistant — deep dive (2026-07-30, ✅ FIXED)

Audited separately and found **non-functional**: it returned confident, plausible output while never reading the uploaded documents. Ten defects, all fixed and verified end-to-end.

| # | Defect | Fix |
| :-- | :--- | :--- |
| 1 | **Documents were never read.** OCR, PDF extraction and voice transcription each hardcoded `gemini-2.0-flash`, which has **zero quota** on this key (`429, limit: 0`). Only the main analysis had a fallback loop, so it kept "working" on no input. Measured on real uploads: **0 characters extracted** | New `services/ai/geminiClient.js` — every Gemini call goes through one client with a model fallback list (`gemini-flash-latest` → `gemini-3.5-flash` → `gemini-2.0-flash`) plus a second retry pass for transient 503s. Verified: same files now yield **1,688 and 3,356 characters** |
| 2 | **Vision API path could never work** — `vision.googleapis.com` rejects API keys outright (`401 "API keys are not supported by this API"`), costing a failed round trip per image | Branch deleted |
| 3 | **False fraud accusations.** OCR failure and "document contains little text" were conflated, so an outage produced `"may be blurred or unreadable"` flags against valid paperwork | `extractionFailed` is now distinct from low text density. Failures report `Extraction Unavailable` and raise **no flag**; warnings are returned to the client as `extractionWarnings` |
| 4 | **AI invented case details from a filename.** With no OCR text the controller substituted the literal string `"General legal intake submission."` and the model generated a title, category and legal domain from it | Falls back only to what the user actually typed. With nothing to analyse it records a `failed` session and returns 422 with actionable guidance |
| 5 | **Could not complete in the app.** Pipeline measured at **40.7s**; Dio's `receiveTimeout` was **15s**, and `RetryInterceptor` retried the POST 3× — up to 4 duplicate sessions and 4× the AI spend per tap | 3-minute timeout on AI routes; `RetryInterceptor` now retries only idempotent methods (plus connection-timeouts that never reached the server), with exponential backoff |
| 6 | **Sequential OCR.** 13–45s per document, so 10 documents could exceed any timeout | `Promise.all`, order preserved; one unreadable document no longer fails the intake |
| 7 | **Fabricated lawyer credentials.** Missing DB values were replaced with rating **4.8**, win rate **88%**, **95** cases, 24 reviews — invented performance data shown to clients choosing legal representation | Unknown values are `null` end-to-end; the review screen renders "Not yet rated" / "Fee on request" or omits the metric |
| 8 | **Every lawyer displayed as "Advocate"** — code read `user.name`, but the schema field is `fullName` (verified `undefined`). The `populate` also projected non-existent `phone`/`avatar` | Corrected to `fullName`/`profileImage`. Verified: real name now returned |
| 9 | **Recommendations always empty** (0 of 2 lawyers matched the filter), so no lawyer was selected → **no appointment and no notification** on case creation, silently | Filter matches on specialisation with a fallback to any active lawyer; the provider no longer pre-selects a phantom lawyer |
| 10 | **Every stored document URL 404'd** — `/uploads/${filename}` omitted the `cases/` sub-folder that multer routes AI uploads into | Derived from `file.path`, so the two cannot drift |

**Two further hard blockers found only by running it** (invisible to static reading):

- **Case creation always failed when a lawyer was selected.** `Appointment.create` used four wrong field names — `appointmentDate` (schema: `date`, required), `type` (schema: `mode`), `status: "Pending"` (enum is lowercase), `mode: "Online"` (enum is `Chat|In-Person`). Mongoose rejected every insert and the request 500'd **after the Case had been written**, orphaning it. Fixed, and appointment creation is now non-fatal.
- **The lawyer was never notified.** The controller called `notificationService.sendNotification(...)` — no such method exists (it is `createAndSendNotification`), with the wrong keys (`userId`/`body`/`relatedId`) and a `type` (`case_update`) absent from the Notification enum. It threw into a swallowing `catch`. Fixed and verified.

Also fixed: `copyWith` could not clear `voiceFile`/`selectedLawyer` (`x ?? this.x`); client model defaulted an empty response to **85% ready**; ~3.5s of fake progress delays claiming stages before upload had begun; no client-side file size/count validation against multer's 10 MB / 10-file limits; the `failed` session status was never set.

**Verified end-to-end:** analyze → 27s, `success: true`, real OCR text, no false flags, correct document URL, real lawyer name with honest nulls; confirm-create → Case + Appointment both created, session `created`; document URL resolves for an entitled user (200) and is refused unauthenticated (401); Gemini client unit-tested for normal call, all-models-down (returns null, no throw) and 429-then-recover.

> ⚠️ **Remaining dependency on you:** `gemini-2.0-flash` reports `limit: 0` — this project has no free-tier allocation, and the healthy models return intermittent 503s under free-tier load. The code now degrades gracefully, but **for a production launch you need billing enabled on the Google Cloud project**, otherwise intake will fail unpredictably under real traffic.
